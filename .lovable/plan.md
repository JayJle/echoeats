# 新增第一步：品类确定（纠正 / 细化 / 推断）

## 目标
需求解析的第一步先单独确定「最终要搜的品类」，再做后面的需求抽取、去重、分类和权重。品类以用户填写的为准，只有在原文明确矛盾或更具体时才改。

## 第一步只分两种情况
1. **用户没填品类** → 根据原文推断 1–2 个最贴合的品类（不允许自动识别时不推断）。
2. **用户填了品类** → 结合填写的品类和后面的描述，生成更完善的品类，可以：
   - **保留**：描述没有冲突，原样使用（如填「拉面」，说想吃鱼介拉面）；
   - **替代**：描述更具体或纠正错字（如「寿司」+「一定要回转」→「回转寿司」；「团DONG」→「天丼」）；
   - **扩展**：在原品类旁再加一个更贴合的品类（总数最多 2 个）。

## 不改的情况（菜品/口味分支）
- 填「拉面」，原文「想吃鱼介拉面 / 豚骨」→ 品类仍是「拉面」，「鱼介拉面」作为菜品条件留在需求里。
- 判断标准：改的是「整家店是什么类型」（回转、立食、放题、居酒屋等），不是「点哪道菜、什么口味」。
- 拿不准时一律不改。

## 用户可见
- 进度页显示「品类已从 寿司 调整为 回转寿司」及原因（引用原文片段），并保留「改回原词」按钮。
- 改回后用原品类重新搜索。

## 后续步骤的衔接
- 后面的需求抽取、召回、排序都用第一步确定的品类。
- 被用来细化品类的那句话（如「要回转」）仍保留为硬条件，用于核验。

## 测试
- 规则单测：寿司+回转→回转寿司；拉面+鱼介拉面→不改；正确输入不改；错字修正；未填+允许→1–2个；未填+不允许→空。
- 小范围真实解析测试 6–8 例（只跑解析，不跑完整搜索，控制成本）。

## 技术细节
- 在 `src/lib/echo.functions.ts` 解析前新增独立的轻量 Qwen 调用 `resolveCuisine`（模型 id 放 `src/lib/models.ts`），输出 `{ cuisines, corrections[{from,to,kind,evidence}] }`。
- 结果全部经 `validateCuisineCorrection`（`src/lib/cuisine-correct.ts`）校验；推断数量在后端硬截到 2；`allowInference=false` 时后端强制不推断。
- 原解析 prompt 中的 `cuisineCorrections` 与推断逻辑移除，改为接收第一步的结果，避免两处各改一次。
- 日志新增 `stage=cuisine-resolve` 的 start/ok/fail、耗时、APPLIED/REJECTED；该步失败时回落为用户原品类并记录。
- 更新 `AGENTS.md` 中品类修正规则为「由独立第一步完成」。
