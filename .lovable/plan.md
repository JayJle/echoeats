## 先回答：为什么会出现“明明写着符合，却显示待核实”？

根因不是前端图标渲染错，而是后端生成 `matchDetails` 时把“状态”和“说明文字”当成两套东西处理：

1. AI 有时返回 `status: unknown`，但在 `note/label` 里又写了“明确符合 / 符合定位 / 满足条件”。
2. 现有兜底函数 `reconcileEvidenceStatus()` 只会识别一小部分正向证据词；像截图里的“明确符合美式牛排店的定位”“符合高端餐厅定位”“没有命中反例关键词”等表达，没有被稳定提升为 `ok`。
3. 另外文案拼接方式把“硬条件待核实：用户条件 → 字段 = 值 — 证据说明”全部塞进一行，所以一旦状态仍是 `unknown`，即使后半句写着“符合”，前半句仍然显示黄色三角和“待核实”。

所以本质是：状态校正规则不够强，且文案生成过于依赖 AI 的原始啰嗦输出，导致“证据语义”和“图标状态”不一致。

## 修改目标

1. 只要匹配详情说明里已经明确表达“符合 / 满足 / 支持 / 命中正向证据 / 未命中反例”，状态必须显示为 `ok`。
2. 只有真正缺资料、无法确认、可能提供、未提及，才显示 `unknown`。
3. 匹配详情文案改短：保留“用户条件 + 简短原因 + 来源/依据”，去掉 `→`、`字段 = 值`、长串英文/日文内部字段名。

## 实施计划

### 1. 加强状态校正规则

修改 `src/lib/echo.functions.ts` 的 `reconcileEvidenceStatus()`：

- 扩充正向匹配识别：
  - “明确符合”
  - “符合…定位”
  - “符合…要求”
  - “满足”
  - “支持”
  - “命中主词/同义词”
  - “没有命中反例关键词”
  - “未命中反例关键词”
  - “no negative keyword hit / no counterexample hit / matches / satisfies / supports”
- 保留不确定识别优先级：
  - “可能提供”
  - “很可能”
  - “未明确提及”
  - “无法确认”
  - “资料不足”
  - “not confirmed / possibly / likely / insufficient”
- 规则顺序：先判断明确不确定，再判断明确正向，避免“可能符合”被误判为 `ok`。

### 2. 对硬条件和非硬条件统一做状态修正

当前硬条件和非硬条件都经过一定程度的校正，但正向词覆盖不足。修复后：

- 硬条件 `hardFilterChecks`：如果 note 写着明确符合，最终 `check.status` 改为 `ok`。
- 非硬条件 `matchDetails`：如果 evidence 写着明确符合，最终 `status` 改为 `ok`。
- 明确冲突仍保持 `fail`，不会被正向词覆盖。

### 3. 简化匹配详情后端文案

新增简短文案清洗函数，例如：

- 去掉开头分类噪音：`硬条件待核实：`、`硬条件：`、`Constraint:`。
- 去掉内部字段表达：`菜系 =`、`餐厅档次 =`、`PrimaryType为`、`reviewHighlights提及` 等。
- 把 `用户条件 → 字段 = 值 — 证据` 压缩成：
  - `谷歌评分 4.0 以上：Google 评分 4.0/5，满足要求`
  - `必须是美式牛排店：资料显示为美式牛排店，符合定位`
  - `要高端一点：评论和 Tabelog 摘要指向高端牛排馆`
  - `必须有 ribeye 牛排：资料未明确提及，待核实`

### 4. 收紧 AI 输出提示词，防止再次产生矛盾

修改 AI rank prompt 中的规则：

- 禁止输出 `字段 = 值`、`PrimaryType`、`reviewHighlights` 这类内部字段名给用户。
- 要求 `hardFilterChecks[].note` 和 `matchDetails[].label` 必须是用户可读短句，建议 20–40 字。
- 明确要求：如果 note/label 写“符合/满足/支持/未命中反例”，status 必须为 `ok`；如果写“可能/很可能/未明确提及”，status 必须为 `unknown`。

### 5. 前端展示保持现有结构，只消费更干净的数据

`src/routes/results.tsx` 目前只是按 `status` 显示 ✓ / ✕ / ⚠，这里不是根因。除非需要做极小的断行/样式保护，否则不改交互结构。

## 验证方式

完成后用截图里的典型句子验证：

- “明确符合美式牛排店的定位” → `ok`，显示 ✓。
- “符合高端餐厅的定位” → `ok`，显示 ✓。
- “作为一家高端美式牛排店，很可能提供” → `unknown`，显示 ⚠。
- “未明确提及 ribeye” → `unknown`，显示 ⚠。
- “没有命中反例关键词”如果对应的是避雷/排除条件 → `ok`，显示 ✓。

不会改搜索、筛选、排序逻辑，只修匹配详情的状态一致性和展示文案。
